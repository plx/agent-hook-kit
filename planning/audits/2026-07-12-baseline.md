## Reproduction

Run from the repository root with the baseline commit checked out:

```sh
cargo metadata --no-deps --format-version 1
cargo tree --workspace --edges normal --depth 1
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace
cargo doc --workspace --no-deps
cargo package -p hookkit-core --allow-dirty --no-verify
cargo package -p hookkit-runtime --allow-dirty --no-verify
```

The final test command includes the external-tool fixture aggregate and therefore
is intentionally expected to vary with `PATH`. After Phase 0, the required
hermetic and opt-in compatibility commands are documented separately in
`docs/testing.md`.

## Workspace and dependency graph

The workspace has eight library/binary crates and four examples:

```text
hookkit-core
├── hookkit-claude ─┐
├── hookkit-codex ──┼── hookkit-common ─┐
└── hookkit-gemini ─┘                   ├── hookkit-runtime
                                       │        │
hookkit-core ── hookkit-pkl-config ─────┼────────┤
                                       └── hookkit-tool-runner

examples:
  claude-sessionstart-context -> core + claude + runtime
  codex-bash-guard             -> core + codex + runtime
  gemini-beforetool-policy     -> core + gemini + runtime
  shared-posttool-autofix      -> core + all native crates + common + runtime
```

The actual runtime crate directly depends on all three legacy native crates and
`hookkit-common`. The runner depends on core, common, runtime, and Pkl config.
There is no Antigravity crate.

## Legacy public API inventory

There are 426 source lines matching a public module, re-export, type, trait,
function, or inherent function declaration in the six protocol/library crates.
The protocol-facing surface is concentrated in these modules:

| Crate | Principal public surface at baseline |
| --- | --- |
| `hookkit-core` | `Harness`, `HookEventKey`, `RawPayload`, `HookkitError`, JSON helpers |
| `hookkit-claude` | `ClaudeHookInput`, 28 known event input structs, typed tool helpers, event-specific response structs, permissive `ClaudeHookOutput`/`OutputEnvelope` |
| `hookkit-codex` | `CodexHookInput`, five known event input structs, `CodexVersion`/`CodexFeatureSet`, Bash helper, permissive output envelope |
| `hookkit-gemini` | `GeminiHookInput`, 11 known event input structs, shell/model helpers, permissive output envelope |
| `hookkit-common` | native-arm input enums, semantic/path views, message types, `CommonHookOutput`, `LoweringPolicy`, universal intent lowering |
| `hookkit-runtime` | `RuntimeContext`, `NativeHookInput`, `NativeHookOutput`, `parse_native`, `run_native`, `run_common`, validation, artifacts, process logging |

The declarations can be re-enumerated without an extra Cargo tool:

```sh
rg -n '^pub (mod|use|struct|enum|trait|fn|type)|^    pub fn' \
  crates/hookkit-{core,claude,codex,gemini,common,runtime}/src -g '*.rs'
```

### Events currently modeled

| Harness | Known input variants | Notes |
| --- | ---: | --- |
| Claude Code | 28 | Includes several newer events, but is not a source-reviewed complete current inventory; also accepts `Unknown` |
| Codex | 5 | `SessionStart`, `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `Stop`; the controlling plan identifies this as obsolete |
| Gemini CLI | 11 | Includes model and tool-selection events; legacy casing/shape assumptions remain |
| Antigravity | 0 | Missing and previously conflated with the Gemini product story |

Each existing native enum also has an `Unknown` arm. That makes payloads
inspectable, but the legacy runtime can pair inputs with overly broad output
envelopes and therefore does not provide event-safe execution.

## Consumers and call sites

- Three single-harness examples call `run_native(Harness, handler)`, then manually
  match umbrella input and output enums.
- `shared-posttool-autofix` calls `run_common`, uses common semantic/path helpers,
  and returns `CommonHookOutput`.
- `hookkit-tool-runner::run_runner` also calls `run_common`.
  `run_common_input` accepts `CommonHookInput`, ignores non-`PostToolUse` events,
  builds `CommonPostToolUseOutput`, and applies `LoweringPolicy`.
- Runtime integration tests execute all four examples and exercise clean,
  auto-fix, manual, missing-tool, operational-failure, and harness-block paths.

These are the migration sites that must remain compiling through temporary
adapters until their named phases remove the legacy APIs.

| Fixture | Harness cases | Installed tool | Difference | Classification |

## Packaging and publication gaps

- Workspace internal dependencies specify only `path`, so dependent crates cannot
  be packaged for crates.io.
- Several manifests inherit neither repository metadata nor complete
  documentation/homepage/keywords/categories/readme metadata.
- No MSRV policy, publish order, changelogs, release automation, or package matrix
  is defined.
- The runner and library share workspace version `0.1.0` without an explicit
  independent release policy.
- Rustdoc currently permits a broken intra-doc link warning.

Phase 6 owns the fix; Phase 0 only makes the gaps explicit.

## Repository concentration

At the baseline there are 973 tracked files totaling 1,108,048 bytes:

- Pkl config/catalog area: 146 files, 232,690 bytes.
- Tool runner area: 731 files, 253,819 bytes.
- Combined: 877 files (90.1% of tracked files), 486,509 bytes (43.9% of tracked
  bytes).

This confirms that the runner/Pkl consumer dominates file count while the core
protocol library remains comparatively small. It is retained as the north-star
consumer through stabilization; extraction is governed by the Phase 7 gate.

## Phase 0 scope decision

The stabilization target inventories every documented binding but promises Rust
native output and runtime support only for command/process bindings explicitly
selected in `contracts/status/stabilization-v1.yaml`. Other bindings remain
catalog-only until a concrete adapter consumer exists. Support and live
verification are separate dimensions; source-reviewed or beta support must not be
described as stable.
